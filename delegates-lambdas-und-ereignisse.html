    7. Delegates, Lambdas und Ereignisse

    Im Kurs von 2008 folgte dieses Kapitel auf das Kapitel über grafische Windows-Forms-Benutzeroberflächen: Ereignisse wurden zunächst im Zusammenhang mit Schaltflächen und Formularen eingeführt, und anschließend lernten die Studierenden, Ereignisse in eigenen Klassen zu erstellen. Das Kapitel über grafische Benutzeroberflächen wurde in dieser Version des Kurses gestrichen. Wir beginnen daher direkt mit dem Konzept, das den gesamten Mechanismus trägt: dem Delegate, also einem Objekt, das eine oder mehrere Methoden referenziert. Alle Beispiele sind Konsolenprogramme.

    In den vergangenen zwanzig Jahren sind Delegates zu einem der am häufigsten verwendeten Werkzeuge der Sprache geworden. Ihre Formulierung ist dank Lambda-Ausdrücken (C# 3) erheblich einfacher geworden; diese haben wir bereits – ohne auf Einzelheiten einzugehen – mit LINQ in Kapitel 5 verwendet: [Where(n => n > 5)] übergibt ein Lambda – und damit ein Delegate – an die Methode [Where]. Dieses Kapitel erklärt, was hinter dieser Syntax steckt. Es schließt mit den Ereignissen, die ebenfalls auf Delegates beruhen. Die grafischen Benutzeroberflächen von .NET (Windows Forms, WPF, .NET MAUI) sowie die Web-Frameworks basieren auf diesem Mechanismus: Ein Klick auf eine Schaltfläche oder das Eintreffen einer HTTP-Anfrage wird abonnierten Methoden signalisiert.

    Die Programme dieses Kapitels sind Single-File-Anwendungen im Ordner [07-delegates]. Sie werden mit [dotnet run delegates-NN.cs] ausgeführt.

    7.1. Vordefinierte Delegate-Typen

    7.1.1. Das Konzept des Delegates

    Ein Delegate-Typ beschreibt ein Muster (auch Prototyp oder Signatur genannt) einer Methode: die Typen ihrer Parameter und den Typ ihres Rückgabewerts. Eine Variable eines Delegate-Typs kann dann jede Methode referenzieren, die diesem Muster entspricht, und sie ausführen.

    Das .NET Framework definiert zahlreiche Delegate-Typen. Der älteste ist [EventHandler], der von allen Ereignissen verwendet wird, die wir am Ende dieses Kapitels besprechen. Er ist wie folgt definiert:

    1
    public delegate void EventHandler(object? sender, EventArgs e);

    Das Schlüsselwort [delegate] macht [EventHandler] zu einem Delegate-Typ. Dieser Typ bezeichnet ein Methodenmuster:

    • dessen erster Parameter ein Objekt vom Typ [object?] ist (das Objekt, das das Ereignis ausgelöst hat, möglicherweise [null]);
    • dessen zweiter Parameter ein Objekt vom Typ [EventArgs] ist (Informationen über das Ereignis);
    • das kein Ergebnis zurückgibt ([void]).

    Eine Methode, die dem durch [EventHandler] definierten Muster entspricht, könnte wie folgt aussehen:

    1
    static void Display(object? sender, EventArgs e) { ... }

    Um ein Objekt vom Typ [EventHandler] zu erstellen, das diese Methode referenziert, können Sie schreiben:

    1
    EventHandler handler = new EventHandler(Display);

    oder, einfacher:

    1
    EventHandler handler = Display;

    In dieser zweiten Schreibweise wird der Methodenname [Display] (eine Methodengruppe, da eine Methode mehrere Überladungen haben kann) vom Compiler automatisch in ein Objekt [EventHandler] umgewandelt: Dies ist die Methodengruppenkonvertierung, die seit C# 2 möglich ist. Der Compiler wählt unter den Überladungen von [Display] diejenige aus, die zur Signatur des Delegates passt. Das Delegate wird dann wie eine Methode ausgeführt: [handler("program", EventArgs.Empty)].

    7.1.2. Die generischen Delegates Func, Action und Predicate

    Vor den Generics (C# 2) musste man für jede Methodensignatur einen eigenen Delegate-Typ definieren. Heute stellt das Framework generische Delegate-Typen bereit, die nahezu alle Anforderungen abdecken:

    Delegate-Typ
    Referenzierte Methoden
    [Action]
    Keine Parameter, kein Rückgabewert: [void M()]
    [Action<T1, ..., T16>]
    1 bis 16 Parameter, kein Ergebnis: [void M(T1 p1, ...)]
    [Func<TResult>]
    Keine Parameter, ein Ergebnis: [TResult M()]
    [Func<T1, ..., T16, TResult>]
    1 bis 16 Parameter, ein Ergebnis vom Typ [TResult] (stets der letzte Typ)
    [Predicate<T>]
    ein Parameter, ein boolesches Ergebnis: [bool M(T p)]
    [Comparison<T>]
    zwei Parameter desselben Typs, ein ganzzahliges Ergebnis: [int M(T x, T y)]

    [Predicate<T>] und [Func<T, bool>] beschreiben dieselbe Signatur, sind aber zwei verschiedene Typen: [Predicate<T>] stammt aus .NET 2 und wird von den Methoden von [List<T>] und [Array] ([FindAll], [RemoveAll], [Exists] …) verwendet, während LINQ, das mit .NET 3.5 eingeführt wurde, [Func<T, bool>] verwendet.

    7.2. Delegate-Typen definieren

    Vordefinierte Typen reichen oft aus, aber Sie können auch eigene Delegate-Typen definieren. Die Anweisung:

    1
    public delegate int Operation(int n1, int n2);

    definiert einen Typ namens [Operation], der ein Methodenmuster darstellt, das zwei ganze Zahlen entgegennimmt und eine ganze Zahl zurückgibt. Im Vergleich zu [Func<int, int, int>] hat der Typ [Operation] einen Namen, der seinen Zweck beschreibt, und seine Parameter haben Namen ([n1], [n2]), die von den Entwicklungswerkzeugen angezeigt werden.

    Eine Variable [op] vom Typ [Operation] dient dazu, eine Liste von Methoden zu speichern, die dem Muster [Operation] entsprechen: Man spricht von einem Multicast-Delegate.

    • Eine Methode vom Typ [f] wird in der Variablen [op] gespeichert mit [op = new Operation(f)] oder, einfacher, [op = f] gespeichert;
    • Um eine Methode [g] zur Liste der bereits registrierten Methoden hinzuzufügen, schreibt man [op += g];
    • Um eine bereits registrierte Methode [h] zu entfernen, schreibt man [op -= h];
    • Die Anweisung [n = op(n1, n2)] führt alle in [op] registrierten Methoden in der Reihenfolge ihrer Registrierung mit den Parametern [n1] und [n2] aus. Das zurückgegebene Ergebnis [n] ist das der zuletzt ausgeführten Methode.

    Der Kurs von 2008 gab an, dass es nicht möglich sei, die Ergebnisse aller Methoden zu erhalten. Es ist möglich, aber nicht mit einem einzigen Aufruf: Man muss die von [GetInvocationList] zurückgegebene Liste der Methoden durchlaufen und sie einzeln aufrufen. In der Praxis geben in einem Multicast-Delegate registrierte Methoden meistens [void] zurück.

// wir definieren ein Objekt vom Typ Operation, um Methoden darin zu registrieren
// wir registrieren die statische Methode Increase
Operation op = Calculations.Increase;
// wir führen das Delegate aus
int n = op(4, 7);
Console.WriteLine($"n={n}");

// Erzeugung eines Objekts c1 vom Typ Calculations
var c1 = new Calculations();
// wir registrieren die Methode Add von c1 im Delegate
op = c1.Add;
// Ausführung des Delegate-Objekts
n = op(2, 3);
Console.WriteLine($"n={n}");
// wir registrieren die Methode Subtract von c1 im Delegate
op = c1.Subtract;
n = op(2, 3);
Console.WriteLine($"n={n}");

// Registrierung zweier Methoden im Delegate (Multicast-Delegate)
op = c1.Add;
op += c1.Subtract;
// Ausführung des Delegate-Objekts: wir erhalten das Ergebnis der letzten Methode
n = op(10, 4);
Console.WriteLine($"n={n}");
// die Ergebnisse aller Methoden mit der Aufrufliste
foreach (Operation method in op.GetInvocationList().Cast<Operation>())
{
    Console.WriteLine($"{method.Method.Name} -> {method(10, 4)}");
}
// wir entfernen eine Methode aus dem Delegate: das Ergebnis kann null sein (Typ Operation?)
Operation? rest = op - c1.Subtract;
// wir führen das Delegate aus, wenn es nicht null ist
if (rest is not null)
{
    n = rest(1, 1);
    Console.WriteLine($"n={n}");
}
// wir entfernen die letzte Methode: das Delegate wird null
Operation? empty = rest - c1.Add;
Console.WriteLine($"empty is null: {empty is null}");
// ?.Invoke führt das Delegate nur aus, wenn es nicht null ist
Console.WriteLine($"empty?.Invoke(1, 1)={empty?.Invoke(1, 1)}");

    return n1 + n2;

Func<int, int, int> subtract = (int n1, int n2) =>
{
    return n1 - n2;
};
Console.WriteLine($"block-bodied lambda: subtract(2, 3)={subtract(2, 3)}");

// 3 - die Parametertypen werden aus dem Ziel-Delegate-Typ abgeleitet
Func<int, int, int> multiply = (n1, n2) => n1 * n2;

// 4 - ein einziger Parameter: die Klammern sind optional
Func<int, int> square = x => x * x;

// 5 - kein Parameter: leere Klammern
Func<string> greet = () => "Hello";
Action beep = () => Console.WriteLine("beep!");

beep();

// 6 - ein Blockrumpf mit mehreren Anweisungen
Action<string, int> repeat = (text, times) =>

    }
    Console.WriteLine();
};

    • Zeilen 11–13: dasselbe mit einem Lambda-Ausdruck. Wir schreiben die Parameterliste, den Operator [=>] (gelesen „ergibt“ oder „sodass“) und dann den Rumpf. Ein Lambda, dessen Rumpf ein von geschweiften Klammern umschlossener Block ist, ist ein Lambda mit Blockrumpf (Anweisungs-Lambda);
    • Zeile 18: Die Parametertypen fehlen. Der Compiler leitet sie vom Ziel-Delegate-Typ [Func<int, int, int>] ab: [n1] und [n2] haben den Typ [int]. Der Rumpf besteht nur aus einem Ausdruck, dessen Wert das Ergebnis des Lambdas ist: Dies ist ein Lambda mit Ausdrucksrumpf (Lambda-Ausdruck). Dies ist die häufigste Form;
    • Zeile 22: Bei einem einzelnen Parameter, dessen Typ nicht angegeben ist, sind die Klammern optional. [x => x * x] wird gelesen „x ergibt x mal x“. Zeile 23: Dasselbe Lambda mit einem einzelnen Parameter vom Typ [string] gibt einen booleschen Wert zurück: Es ist ein [Predicate<string>];
    • Zeilen 27–28: Ohne Parameter werden leere Klammern verwendet. Ein Lambda, dessen Rumpf ein Methodenaufruf ([void]) ist, eignet sich für ein Delegate ([Action]);
    • Zeilen 33–39: Ein Lambda mit Blockrumpf kann beliebige Anweisungen enthalten: Deklarationen, Schleifen, Tests usw.;
    • Zeile 44: Das Unterstrichzeichen [_] bezeichnet einen ignorierten Parameter (Discard, C# 9). Es wird verwendet, wenn die Signatur des Delegates Parameter verlangt, die das Lambda nicht benötigt, was bei Ereignishandlern häufig vorkommt;
    • Zeile 49: Die häufigste Verwendung von Lambdas besteht darin, sie direkt als Parameter an eine Methode zu übergeben, die ein Delegate erwartet. Vergleichen Sie mit [delegates-01.cs]: Es ist nicht mehr nötig, eine Methode [IsEven] zu schreiben;
    • Zeile 50: ein Lambda vom Typ [Comparison<int>] , das den üblichen Vergleich umkehrt: Die Liste wird absteigend sortiert.

    Fassen wir die Formen eines Lambda-Ausdrucks zusammen:

    Form
    Beispiel
    typisierte Parameter, Blockrumpf
    [(int a, int b) => { return a + b; }]
    nicht typisierte Parameter, Ausdrucksrumpf
    [(a, b) => a + b]
    ein einzelner nicht typisierter Parameter
    [x => x * x]
    keine Parameter
    [() => "Hello"]
    ignorierte Parameter

    Die Parameter sind entweder alle typisiert oder alle nicht typisiert: Beides zu mischen ist nicht möglich. In diesem Kurs verwenden wir Lambdas statt anonymer Methoden, die heute nur noch in seltenen Fällen nützlich sind.

    7.5. Ereignisbehandlung

    7.5.1. Das Ereignismodell von .NET

    Delegaten dienen zur Definition von Ereignissen. Eine Klasse [C1] kann ein Ereignis [Evt1] wie folgt definieren:

    • Ein Delegattyp wird innerhalb oder außerhalb der Klasse [C1] definiert:
    1
    delegate void Evt(T1 param1, T2 param2, ...);
    • Die Klasse [C1] definiert ein Feld dieses Delegattyps:
    1
    public Evt? Evt1;
    • Wenn eine Instanz [c1] der Klasse [C1] ein Ereignis signalisieren möchte, führt sie ihren Delegaten [Evt1] aus und übergibt ihm die Parameter, die der Typ [Evt] vorgibt. Alle im Delegaten [Evt1] registrierten Methoden werden dann mit diesen Parametern ausgeführt. Man sagt, sie seien über das Ereignis [Evt1] benachrichtigt worden;
    • wenn ein Objekt [c2], das das Objekt [c1] verwendet, über das Ereignis [Evt1] des Objekts [c1] benachrichtigt werden möchte, registriert es eine seiner Methoden, [c2.M], beim Delegaten [c1.Evt1]. Seine Methode [c2.M] wird dann jedes Mal ausgeführt, wenn das Ereignis [Evt1] beim Objekt [c1] eintritt. Es kann sich auch wieder abmelden, wenn es nicht mehr benachrichtigt werden möchte;
    • da der Delegat [c1.Evt1] mehrere Methoden registrieren kann, können sich verschiedene Objekte [ci] bei [c1.Evt1] anmelden, um über das Ereignis benachrichtigt zu werden.

    In diesem Szenario haben wir:

    • eine Klasse, die ein Ereignis signalisiert (man sagt auch „veröffentlicht“ oder „auslöst“);
    • Klassen, die über dieses Ereignis benachrichtigt werden. Man sagt, sie abonnieren das Ereignis;
    • einen Delegattyp, der die Signatur der Methoden definiert, die über das Ereignis benachrichtigt werden. Diese Methoden heißen Ereignishandler.

    Dies ist das Entwurfsmuster Observer: Der Sender kennt seine Abonnenten nicht, er benachrichtigt sie lediglich.

    Das .NET-Framework definiert eine Standardsignatur für einen Ereignisdelegaten:

    1
    public delegate void MyEventHandler(object? sender, EventArgs e);
    • [sender]: das Objekt, das das Ereignis ausgelöst hat;
    • [e]: ein Objekt vom Typ [EventArgs] oder von einem abgeleiteten Typ, das Informationen über das Ereignis liefert;
    • Per Konvention endet der Name des Delegattyps auf [EventHandler].

    Außerdem definiert es eine Standardschreibweise, um in einer Klasse ein Ereignis vom Typ [MyEventHandler] zu deklarieren:

    Das Feld [Evt1] hat den Delegattyp. Das Schlüsselwort [event] schränkt die Operationen ein, die darauf ausgeführt werden können:

    • Von außerhalb der Klasse [C1] sind nur die Operationen [+=] und [-=] erlaubt. Dadurch wird verhindert, dass die abonnierten Methoden von anderen Objekten überschrieben oder gelöscht werden (etwa versehentlich durch die Schreibweise [=] statt [+=]). Man kann nur abonnieren ([+=]) oder abbestellen ([-=]);
    • nur die Klasse [C1] kann den Delegaten ausführen, das heißt das Ereignis auslösen: [Evt1?.Invoke(this, e)].

    Wenn Sie versuchen, außerhalb der Klasse [c1.Evt1 = null;] oder [c1.Evt1(null, EventArgs.Empty);] zu schreiben, antwortet der Compiler mit: [error CS0070: The event 'C1.Evt1' can only appear on the left hand side of += or -= (except when used from within the type 'C1')].

    Statt für jedes Ereignis einen eigenen Delegattyp zu definieren, verwendet man den vordefinierten generischen Delegaten:

    1
    public delegate void EventHandler<TEventArgs>(object? sender, TEventArgs e);

    Der Typ [TEventArgs] ist der des zweiten Parameters, des Objekts, das das Ereignis beschreibt. Mit diesem generischen Delegaten folgt die Deklaration eines Ereignisses [X] in einer Klasse [C] dem folgenden empfohlenen Muster:

    • einen von [XEventArgs] abgeleiteten Typ [EventArgs] definieren, der die Informationen zum Ereignis [X] kapselt;
    • in der Klasse [EventHandler<XEventArgs>] ein Ereignis vom Typ [C] definieren;
    • in der Klasse [C] eine geschützte, virtuelle Methode [protected virtual void OnX(XEventArgs e)] definieren, die das Ereignis [X] an die Abonnenten veröffentlicht. Sie ist virtuell, damit eine abgeleitete Klasse die Art der Veröffentlichung ändern kann.

    Im Jahr 2008 musste der Typ [TEventArgs] von [EventArgs] abgeleitet sein (Einschränkung [where TEventArgs : EventArgs]). Diese Einschränkung wurde in .NET Framework 4.5 entfernt: Jeder Typ ist zulässig, auch ein [record]. Per Konvention leitet man jedoch weiterhin von [EventArgs] ab. Beachten Sie, dass ein [record] nicht von [EventArgs] abgeleitet werden kann: Ein [record] kann nur von einem anderen [record] erben (Fehler: [CS8864: Records may only inherit from object or another record]). Wir verwenden daher eine gewöhnliche Klasse.

public static class Tools
{
    // filtert eine Sequenz mit einem Prädikat: das Äquivalent von Where
    public static IEnumerable<T> Filter<T>(IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (T element in source)
        {
            if (predicate(element))
            {
                // das Element wird an den Aufrufer zurückgegeben; die Iteration wird hier fortgesetzt
                yield return element;
            }
        }
    }
}

public static class Extensions
{
    // Erweiterungsmember (C# 14) von IEnumerable<T>
    extension<T>(IEnumerable<T> source)
    {
        // Filter als Erweiterungsmethode: wir verwenden Tools.Filter wieder
        public IEnumerable<T> Filter(Func<T, bool> predicate) => Tools.Filter(source, predicate);

        // transformiert jedes Element: das Äquivalent von Select
        public IEnumerable<TResult> Transform<TResult>(Func<T, TResult> transformation)
        {
            foreach (T element in source)
            {
                yield return transformation(element);
            }
        }
    }
}

Genau das tut Entity Framework Core, mit dem wir uns in Kapitel 11 beschäftigen werden. Schreibt man eine LINQ-Abfrage auf eine Datenbanktabelle, zum Beispiel [context.Brackets.Where(t => t.Limit > 20000)], so ist die verwendete Methode [Where] nicht die von [IEnumerable<T>] , sondern die von [IQueryable<T>], deren Parameter ein [Expression<Func<T, bool>>] ist. EF Core durchläuft diesen Baum, genau wie unsere Methode [Display], und übersetzt ihn in eine SQL-Klausel [WHERE limits > 20000], die vom Datenbankserver ausgeführt wird. Dasselbe, gleich geschriebene Lambda wird also je nach Typ des Parameters, den es erhält, entweder zu .NET-Code oder zu SQL-Code.

    7.8. Fazit

    Die wichtigsten Punkte dieses Kapitels:

    • Ein Delegat ist ein Objekt, das auf eine oder mehrere Methoden mit einer bestimmten Signatur verweist. Die vordefinierten Typen [Func<>], [Action<>] und [Predicate<T>] machen die Definition eigener Delegattypen in der Regel überflüssig;
    • Lambda-Ausdrücke erlauben es, die Methode direkt an der Stelle zu schreiben, an der der Delegat erzeugt wird. Sie erfassen die Variablen ihrer Umgebung (Vorsicht bei [for]-Schleifen);
    • Ein Delegat kann eine Schnittstelle mit nur einer Methode ersetzen und bietet dabei mehr Flexibilität;
    • ein Ereignis ist ein durch das Schlüsselwort [event] geschützter Delegat: Man abonniert es mit [+=], bestellt es mit [-=] ab, und nur die Klasse, die es deklariert, löst es aus, und zwar mit [Evt?.Invoke(this, e)];
    • LINQ beruht auf Methoden, die Delegaten annehmen, und EF Core beruht auf Ausdrucksbäumen.

    Auf Delegaten kommen wir in den folgenden Kapiteln zurück: Ein Task ([Task.Run]) führt einen Delegaten in einem anderen Thread aus (Kapitel 8 und 9), und die ASP.NET-Core-Webdienste verknüpfen Lambdas mit HTTP-Adressen (Kapitel 13).
