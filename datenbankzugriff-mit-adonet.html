    10. Datenbankzugriff mit ADO.NET

    10.1. Der ADO.NET-Connector

    Kehren wir zur Schichtenarchitektur zurück, die seit Kapitel 6 wiederholt verwendet wird. Bisher hat die Schicht [dao] der Anwendung [Tax] drei Arten von Datenquellen genutzt:

    • im Code fest eingebaute Daten ([HardwiredTax]);
    • Daten aus einer Textdatei ([FileTax]);
    • Daten aus einer JSON-Datei ([JsonTax]).

    In diesem Kapitel untersuchen wir den Fall, dass die Daten aus einer Datenbank stammen. Die Architektur sieht dann wie folgt aus:

    Im obigen Schema kommuniziert die Schicht [dao] [1] mit dem DBMS (Datenbankmanagementsystem) [3], das die Datenbank [4] verwaltet, und zwar über eine Klassenbibliothek, die für das verwendete DBMS spezifisch ist [2]. Diese Bibliothek implementiert Standardfunktionen, die unter dem Namen ADO.NET zusammengefasst sind (ADO steht für „ActiveX Data Objects“, den Namen der Datenzugriffstechnologie, die ihr unter Windows voranging). Man spricht von einem „Datenprovider“ oder einem „Connector“. Alle gängigen DBMS besitzen einen ADO.NET-Connector.

    Die Klassen eines Connectors sind nach dem DBMS benannt: [MySqlConnection] für MySQL, [SqlConnection] für SQL Server, [NpgsqlConnection] für PostgreSQL … Verwendet die Schicht [dao] diese Klassen, enthält ihr Code den Namen des Connectors, und ein Wechsel des DBMS erfordert ihre Änderung. Diese Architektur ist zugleich effizient – weil ein für ein bestimmtes DBMS geschriebener Connector es bestmöglich nutzen kann – und starr, weil ein Wechsel des DBMS eine Änderung der Schicht [dao] erfordert. Dieser zweite Punkt ist zu relativieren: Unternehmen wechseln ihr DBMS nicht sehr oft. Außerdem werden wir sehen, dass ADO.NET ab .NET 2.0 einen „generischen Connector“ bietet, der Flexibilität ermöglicht, ohne Leistung zu opfern.

    Der Kurs von 2008 verwendete nacheinander die DBMS SQL Server Compact (von Microsoft inzwischen eingestellt), SQL Server 2005 Express, MySQL 5 und anschließend die ODBC- und OLE-DB-Treiber, wobei die Datenbanken mit den Assistenten von Visual Studio erstellt wurden. Hier verwenden wir ein einziges DBMS, MySQL 8, das der Anhang mit Laragon installiert, und einen seiner heute am weitesten verbreiteten ADO.NET-Connectors, MySqlConnector. Die Datenbanken werden durch SQL-Skripte erstellt, die mit dem Kommandozeilenclient [mysql] ausgeführt werden; der Anhang zeigt außerdem, wie man sie mit dem grafischen Client HeidiSQL erstellt, der in Laragon enthalten ist.

    10.2. Die zwei Arten, eine Datenquelle zu nutzen

    ADO.NET erlaubt es, eine Datenquelle auf zwei unterschiedliche Arten zu nutzen:

    • im verbundenen Modus;
    • im getrennten Modus.

    Im verbundenen Modus führt die Anwendung Folgendes aus:

    • Sie öffnet eine Verbindung zur Datenquelle;
    • sie arbeitet mit der Datenquelle im Lese-/Schreibmodus;
    • sie schließt die Verbindung.

    Im getrennten Modus führt die Anwendung Folgendes aus:

    • Sie öffnet eine Verbindung zur Datenquelle;
    • sie ruft eine Kopie aller oder eines Teils der Daten der Quelle in den Speicher ab;
    • sie schließt die Verbindung;
    • sie arbeitet mit der Kopie der Daten im Speicher und liest und schreibt dort;
    • wenn die Arbeit beendet ist, öffnet sie eine Verbindung, sendet die geänderten Daten zur Aktualisierung an die Datenquelle und schließt die Verbindung.

    Der getrennte Modus beruhte auf den Klassen [DataSet] (einer kleinen Datenbank im Speicher mit ihren Tabellen [DataTable], ihren Zeilen [DataRow] und ihren Beziehungen) und [DataAdapter] (der Brücke zwischen einem [DataSet] und der Datenbank). Diese Klassen existieren in .NET 10 weiterhin, werden in neuen Anwendungen aber nur selten verwendet: Die Arbeit mit einer Kopie der Daten im Speicher und das anschließende Speichern der Änderungen übernimmt heute ein ORM („Object-Relational Mapper“), das gewöhnliche C#-Objekte statt Tabellenzeilen bearbeitet. Das ORM von .NET, Entity Framework Core, ist Gegenstand von Kapitel 11. Wie im Kurs von 2008 konzentrieren wir uns hier nur auf den verbundenen Modus, auf dem Entity Framework Core beruht.

    10.3.2. Die vier grundlegenden Befehle der Sprache SQL

    SQL („Structured Query Language“) ist eine teilweise standardisierte Sprache zum Abfragen und Aktualisieren von Datenbanken. Alle DBMS-Dialekte halten sich an den standardisierten Teil von SQL, ergänzen die Sprache aber um proprietäre Erweiterungen, die ihre jeweiligen Besonderheiten nutzen. Zwei Beispiele dafür sind uns bereits begegnet: Die automatische Erzeugung von Primärschlüsseln und die zulässigen Datentypen für Tabellenspalten hängen häufig vom DBMS ab.

    Die vier grundlegenden Befehle der Sprache SQL, die wir hier vorstellen, sind standardisiert und werden von allen DBMS unterstützt:

    Befehl
    Aufgabe
    [select col1, col2, … from table1, table2, … where condition order by expression]
    Die Abfrage, mit der Daten aus einer Datenbank abgerufen werden. Nur die Schlüsselwörter [select] und [from] sind obligatorisch. Mit allen Tabellen, die auf das Schlüsselwort [from] folgen, wird ein Join durchgeführt; nur die Spalten, die auf das Schlüsselwort [select] folgen, werden beibehalten; nur die Zeilen, die die Bedingung des Schlüsselworts [where] erfüllen, werden beibehalten; die resultierenden Zeilen, sortiert nach dem Ausdruck im Schlüsselwort [order by], bilden das Ergebnis der Abfrage. Dieses Ergebnis ist eine Tabelle.
    [insert into table(col1, col2, …) values (val1, val2, …)]
    Fügt eine Zeile in [table] ein. [(col1, col2, …)] gibt die Spalten der Zeile an, die mit den Werten aus [(val1, val2, …)] gefüllt werden.
    [update table set col1=val1, col2=val2, … where condition]
    Aktualisiert die Zeilen in [table] anhand von [condition] (alle Zeilen, wenn kein [where] angegeben ist). Für diese Zeilen wird die Spalte [coli] auf [vali] gesetzt.
    [delete from table where condition]
    Löscht alle Zeilen aus [table] , die [condition] erfüllen (alle Zeilen, wenn kein [where] angegeben ist).

    10.3.3. Basisklassen von ADO.NET für den verbundenen Modus

    Kehren wir zum Schema einer Anwendung zurück, die über einen ADO.NET-Connector auf eine Datenbank zugreift:

    Im verbundenen Modus führt die Anwendung Folgendes aus:

    • Sie öffnet eine Verbindung zur Datenquelle;
    • sie arbeitet mit der Datenquelle im Lese-/Schreibmodus;
    • sie schließt die Verbindung.

    An diesen Operationen sind im Wesentlichen drei Arten von Objekten beteiligt:

    • die Verbindung, die die Eigenschaften und Methoden der Datenbankverbindung kapselt;
    • der Befehl, der die Eigenschaften und Methoden des ausgeführten SQL-Befehls kapselt;
    • der Data Reader, der die Eigenschaften und Methoden des Ergebnisses eines SQL-Befehls [select] kapselt.

    Jeder Connector definiert seine eigenen Klassen ([MySqlConnection], [MySqlCommand], [MySqlDataReader] für MySqlConnector), die von abstrakten Klassen abgeleitet sind, die allen Connectors gemeinsam sind und im Namespace [System.Data.Common] definiert werden: [DbConnection], [DbCommand], [DbDataReader]. Der Kurs von 2008 stellte die Schnittstellen [IDbConnection], [IDbCommand] und [IDataReader] aus dem Namespace [System.Data] vor, die diese Klassen implementieren. Heute werden abstrakte Klassen bevorzugt: Sie bieten mehr Funktionalität als Schnittstellen, denen sich keine Methoden mehr hinzufügen ließen, ohne bestehende Connectors zu beschädigen (Standardschnittstellenmethoden gab es noch nicht). Die asynchronen Versionen der Methoden ([OpenAsync], [ExecuteReaderAsync], [ReadAsync] …) beispielsweise existieren nur in den abstrakten Klassen.

    Sie dient zum Ausführen eines SQL-Befehls oder einer gespeicherten Prozedur. Die Methoden M und Eigenschaften P dieser Klasse, die wir verwenden werden, sind die folgenden:

    Name
    Typ
    Rolle
    [CommandType]
    P
    legt fest, was ausgeführt werden soll. Seine Werte stammen aus der Enumeration [CommandType]: [CommandType.Text] führt den SQL-Befehl aus, der in der Eigenschaft [CommandText] definiert ist (dies ist der Standardwert); [CommandType.StoredProcedure] führt eine gespeicherte Prozedur der Datenbank aus.
    [CommandText]
    P
    der Text des auszuführenden SQL-Befehls, wenn [CommandType] gleich [CommandType.Text] ist, bzw. der Name der auszuführenden gespeicherten Prozedur, wenn [CommandType] gleich [CommandType.StoredProcedure] ist.

    P

    P

    M
    Führt einen SQL-Befehl [select] aus. Dabei wird ein Objekt [DbDataReader] zurückgegeben, das das Ergebnis von [select] darstellt.

    10.3.7. Ausführen einer SELECT-Abfrage

    Das Ausführen von SQL-Befehlen umfasst die folgenden Schritte:

    • Verbindung zur Datenbank herstellen;
    • die SQL-Befehle an die Datenbank senden;
    • die Ergebnisse der SQL-Befehle verarbeiten;
    • die Verbindung schließen.

    Die Schritte 2 und 3 können wiederholt werden; die Verbindung wird erst am Ende der Datenbankverarbeitung geschlossen. Offene Verbindungen sind in einem DBMS begrenzte Ressourcen: Man muss sparsam mit ihnen umgehen und bemüht sich stets, die Lebensdauer einer offenen Verbindung zu begrenzen. In unserem Programm wird die Verbindung nach jedem SQL-Befehl geschlossen, und für den nächsten Befehl wird eine neue Verbindung geöffnet.

    Das Öffnen einer Verbindung ist jedoch aufwendig: Es erfordert den Aufbau einer Netzwerkverbindung zum Server, gegebenenfalls das Aushandeln einer Verschlüsselung und eine Authentifizierung. Um diesen Aufwand zu verringern, verwalten die Konnektoren einen Verbindungspool: Wenn die Anwendung eine Verbindung schließt, schließt der Konnektor sie nicht wirklich, sondern gibt sie an einen Pool zurück; wenn die Anwendung mit derselben Verbindungszeichenfolge eine neue Verbindung öffnet, erhält sie eine der bereits aufgebauten Verbindungen aus dem Pool. Der Vorteil dieses Systems ist, dass es für den Entwickler transparent ist: Das Programm muss nicht geändert werden, um es zu nutzen. Der Pool ist in MySqlConnector (wie in anderen aktuellen Konnektoren) standardmäßig aktiviert und wird über Parameter der Verbindungszeichenfolge konfiguriert ([Pooling], [MaximumPoolSize], [MinimumPoolSize] …). Es empfiehlt sich daher, zu Beginn jeder Operation eine Verbindung zu öffnen und sie am Ende mit einem [using] zu schließen.

    Der „generische Konnektor“ stellt den Anwendungen, die ihn nutzen, eine Standardschnittstelle zur Verfügung, ohne Leistung einzubüßen, da er auf den DBMS-spezifischen Konnektoren aufsetzt.     10.4.3. Welchen Konnektor sollte man wählen?

    Wir haben zwei Möglichkeiten kennengelernt, einen ADO.NET-Konnektor zu verwenden:

    • die Klassen des Konnektors direkt verwenden: Die Schicht [dao] hängt vom Konnektor ab. Ein Wechsel des DBMS erfordert eine Änderung der Schicht [dao];
    • den generischen Konnektor verwenden: Die Schicht [dao] kennt nur die abstrakten Klassen und den Invariant-Namen des Konnektors, der aus einer Konfigurationsdatei gelesen werden kann.

    Der generische Konnektor scheint also die ideale Lösung zu sein. In der Praxis kann er jedoch nicht alle Besonderheiten eines DBMS verbergen:

    • Das SQL selbst unterscheidet sich von einem DBMS zum anderen, sobald man über die Grundbefehle hinausgeht: Erzeugung von Primärschlüsseln, Begrenzung der Anzahl der gelieferten Zeilen ([limit 10] bei MySQL, [top 10] oder [offset … fetch] bei SQL Server), Spaltentypen, Datumsfunktionen usw.;
    • Die Syntax der Parameter parametrisierter Abfragen variiert: [@name] bei SQL Server, MySQL und SQLite, aber [?] (Positionsparameter, ohne Namen) bei den ODBC- und OLE-DB-Treibern und beim MySQL-Konnektor von 2008, und [$1], [$2] … im nativen SQL von PostgreSQL (Npgsql akzeptiert auch [@name]). Bei Positionsparametern ist die Reihenfolge wichtig, in der die Parameter der Sammlung [Parameters] hinzugefügt werden; bei benannten Parametern spielt die Reihenfolge keine Rolle;
    • Schließlich sind die Ausnahmen [DbException], deren Fehlercodes vom DBMS abhängen.

    Der Kurs von 2008 nannte Frameworks, die diese Einschränkungen überwinden: Spring.NET, iBatis.NET, NHibernate und LINQ to SQL. Spring.NET und iBatis.NET werden nicht mehr gepflegt; LINQ to SQL wird nicht mehr weiterentwickelt und existiert im aktuellen .NET nicht; NHibernate gibt es weiterhin. Heute werden vor allem die folgenden verwendet:

    • Entity Framework Core, der ORM von Microsoft, eingeführt in Kapitel 11: Die Schicht [dao] arbeitet mit C#-Objekten und schreibt ihre Abfragen in LINQ; EF Core erzeugt das SQL, das für das jeweilige DBMS spezifisch ist;
    • Dapper, ein „Micro-ORM“, ergänzt die ADO.NET-Verbindungen um Erweiterungsmethoden, die die Zeilen eines [select] direkt in C#-Objekte umwandeln. Das SQL schreibt man weiterhin selbst, die Schleifen über den Reader jedoch nicht mehr.

    Alle diese Werkzeuge beruhen auf ADO.NET-Konnektoren: Das Verständnis von ADO.NET bleibt nützlich, um zu verstehen, was sie tun, und um Probleme mit ihnen zu beheben.

// Einfügen eines Artikel-Arrays mit einer parametrisierten Abfrage
static void InsertArticles(string connectionString, Article[] articles)
{
    using var connection = new MySqlConnection(connectionString);
    connection.Open();
    // die parametrisierte Abfrage: @name, @price, @cs, @ms sind ihre Parameter
    const string Query = "insert into articles(name, price, currentstock, minimumstock) values(@name, @price, @cs, @ms)";
    using var command = new MySqlCommand(Query, connection);
    // Deklaration der Parameter: Name und SQL-Typ
    command.Parameters.Add("@name", MySqlDbType.VarChar, 30);
    command.Parameters.Add("@price", MySqlDbType.Decimal);
    command.Parameters.Add("@cs", MySqlDbType.Int32);
    command.Parameters.Add("@ms", MySqlDbType.Int32);
    // Vorbereitung (Kompilierung) der Abfrage durch das DBMS
    command.Prepare();
    // Einfügen der Zeilen: nur der Wert der Parameter ändert sich
    foreach (Article article in articles)
    {
        command.Parameters["@name"].Value = article.Name;
        command.Parameters["@price"].Value = article.Price;
        command.Parameters["@cs"].Value = article.CurrentStock;
        command.Parameters["@ms"].Value = article.MinimumStock;
        command.ExecuteNonQuery();
    }
    Console.WriteLine($"{articles.Length} article(s) inserted");
}

static List<Article> GetArticles(string connectionString, string pattern)
{
    using var connection = new MySqlConnection(connectionString);
    connection.Open();
    using var command = new MySqlCommand(
        "select id, name, price, currentstock, minimumstock from articles where name like @pattern order by id", connection);
    // Deklaration des Parameters und seines Werts in einer einzigen Anweisung

    }
    return list;
}

    10.6. Transaktionen

    10.6.1. Allgemeines

    Eine Transaktion ist eine Folge von SQL-Befehlen, die „atomar“ ausgeführt werden:

    • entweder gelingen alle Operationen;
    • oder eine von ihnen schlägt fehl, und dann werden alle vorhergehenden Operationen rückgängig gemacht.

    Am Ende werden entweder alle Operationen einer Transaktion erfolgreich angewendet oder keine. Das klassische Beispiel ist eine Banküberweisung: Die Abbuchung von einem Konto und die Gutschrift auf einem anderen müssen beide ausgeführt werden oder keine von beiden. Steuert die Anwendung die Transaktion selbst, bestätigt sie sie mit einem Befehl [COMMIT] oder macht sie mit einem Befehl [ROLLBACK] rückgängig.

    In unseren bisherigen Beispielen haben wir keine Transaktion verwendet. Und doch gab es Transaktionen, denn in einem DBMS wird ein SQL-Befehl immer innerhalb einer Transaktion ausgeführt. Startet die Anwendung nicht selbst eine explizite Transaktion, verwendet das DBMS eine implizite Transaktion. Dann gibt es zwei Fälle:

    • Jeder SQL-Befehl ist Teil einer Transaktion, die das DBMS vor dem Befehl öffnet und danach bestätigt. Man spricht vom Autocommit-Modus. Er verhält sich so, als würde die Anwendung für jeden SQL-Befehl eine Transaktion erstellen;
    • Das DBMS befindet sich nicht im Autocommit-Modus: Es startet mit dem ersten SQL-Befehl, der außerhalb einer Transaktion abgesetzt wird, eine implizite Transaktion und überlässt es der Anwendung, sie abzuschließen. Alle folgenden SQL-Befehle sind Teil dieser impliziten Transaktion, die durch verschiedene Ereignisse (Schließen der Verbindung, Start einer neuen Transaktion usw.) nach DBMS-spezifischen Regeln beendet werden kann. Dieser Modus sollte vermieden werden.

    Der Standardmodus wird durch die Konfiguration des DBMS bestimmt. MySQL arbeitet mit der standardmäßig verwendeten Speicher-Engine InnoDB im Autocommit-Modus.

    Befehle verschiedener Benutzer werden gleichzeitig in Transaktionen ausgeführt, die parallel laufen. Operationen, die eine Transaktion durchführt, können die einer anderen beeinflussen. Es gibt vier Isolationsstufen zwischen den Transaktionen verschiedener Benutzer:

    • Read Uncommitted;
    • Read Committed;
    • Repeatable Read;
    • Serializable.

    Read Uncommitted

    Diese Isolationsstufe ist auch als „Dirty Read“ bekannt. Hier ein Beispiel dafür, was in diesem Modus passieren kann:

    • Ein Benutzer namens U1 startet eine Transaktion auf der Tabelle T;
    • ein Benutzer namens U2 startet eine Transaktion auf derselben Tabelle T;
    • Benutzer U1 ändert Zeilen der Tabelle T, hat die Änderungen aber noch nicht bestätigt;
    • Benutzer U2 „sieht“ diese Änderungen und trifft Entscheidungen auf der Grundlage dessen, was er sieht;
    • Benutzer U1 macht seine Transaktion mit [ROLLBACK] rückgängig.

    In Schritt 4 hat Benutzer U2 eine Entscheidung auf der Grundlage von Daten getroffen, die sich später als falsch herausstellten.

    Read Committed

    Diese Isolationsstufe vermeidet die vorherige Falle: In Schritt 4 „sieht“ Benutzer U2 die Änderungen, die Benutzer U1 an der Tabelle T vorgenommen hat, nicht. Er sieht sie erst, nachdem U1 seine Transaktion mit einem [COMMIT] bestätigt hat. In diesem Modus kann jedoch die folgende Situation eintreten:

    • Ein Benutzer U1 startet eine Transaktion auf der Tabelle T;
    • ein Benutzer U2 startet eine Transaktion auf derselben Tabelle T;
    • Benutzer U2 führt ein [select] aus, um den Durchschnitt der Spalte C für die Zeilen von T zu berechnen, die eine bestimmte Bedingung erfüllen;
    • Benutzer U1 ändert ([update]) bestimmte Werte der Spalte C von T und bestätigt die Änderungen ([commit]);
    • Benutzer U2 wiederholt dasselbe [select] wie in Schritt 3. Er stellt fest, dass sich der Durchschnitt der Spalte C aufgrund der von U1 vorgenommenen Änderungen geändert hat.

    Benutzer U2 sieht nun nur noch die von U1 bestätigten Änderungen, doch obwohl er sich weiterhin in derselben Transaktion befindet, liefern zwei identische Operationen unterschiedliche Ergebnisse. Diese Situation nennt man „Non-repeatable Read“ (nicht wiederholbares Lesen). Sie ist für jeden problematisch, der eine konsistente Sicht auf die Tabelle T benötigt.

    Repeatable Read

    Bei dieser Isolationsstufe ist garantiert, dass ein Benutzer bei Lesezugriffen auf die Datenbank dieselben Ergebnisse erhält, solange er sich in derselben Transaktion befindet. Er arbeitet mit einem „Schnappschuss“ der Daten, der die Änderungen anderer Transaktionen nicht widerspiegelt, auch wenn diese bestätigt wurden. Er sieht diese Änderungen erst, nachdem er seine eigene Transaktion beendet hat.

    Diese Isolationsstufe ist in der Theorie noch nicht perfekt: Eine andere Transaktion kann Zeilen hinzufügen ([insert]), die die Bedingung aus Schritt 3 erfüllen, was das Ergebnis eines späteren Lesezugriffs verändern würde. Diese Zeilen nennt man „Phantomzeilen“ (Phantom Reads). Dies ist die Standard-Isolationsstufe von MySQL (InnoDB), die bei einfachen Lesezugriffen auch Phantomzeilen verhindert.

    Serializable

    In diesem Isolationsmodus sind die Transaktionen vollständig voneinander isoliert: Das Ergebnis zweier gleichzeitig ausgeführter Transaktionen ist dasselbe, als wären sie nacheinander ausgeführt worden. Dazu sperrt das DBMS die gelesenen Daten und lässt Transaktionen, die versuchen, sie zu ändern, warten (oder fehlschlagen). Diese Stufe verringert die Parallelität und damit die Leistung.

    Die vier Isolationsstufen sind nicht in allen DBMS verfügbar. Die Standard-Isolationsstufe ist in der Regel Read Committed (SQL Server, PostgreSQL, Oracle) oder Repeatable Read (MySQL). Die gewünschte Isolationsstufe einer Transaktion kann ausdrücklich angegeben werden, wenn die Anwendung die Transaktion erstellt.

// Einfügen eines Artikel-Arrays innerhalb einer Transaktion
static void InsertArticlesInTransaction(string connectionString, Article[] articles)
{
    using var connection = new MySqlConnection(connectionString);
    connection.Open();
    // Beginn der Transaktion
    using MySqlTransaction transaction = connection.BeginTransaction(IsolationLevel.ReadCommitted);
    try
    {
        using MySqlCommand command = CreateInsertCommand(connection);
        // der Befehl muss innerhalb der Transaktion ausgeführt werden
        command.Transaction = transaction;
        foreach (Article article in articles)
        {
            InsertArticle(command, article);
        }
        // alles ist gut gegangen: wir bestätigen die Transaktion (Commit)
        transaction.Commit();
        Console.WriteLine("transaction committed...");
    }
    catch (MySqlException ex)
    {
        // ein Einfügen ist fehlgeschlagen: wir machen die Transaktion rückgängig
        transaction.Rollback();
        Console.WriteLine($"transaction rolled back ({ex.Message})");
    }
}

    • Zeilen 34–39: ein Batch aus zwei Befehlen [select];
    • Zeile 42: Der Batch wird von [ExecuteReaderAsync] ausgeführt, das einen einzigen Reader für beide Ergebnisse zurückgibt;
    • Zeile 49: Nachdem die Zeilen des ersten Ergebnisses gelesen wurden, setzt [NextResultAsync] den Reader auf das nächste Ergebnis.

    Dieselbe Wirkung ließe sich erzielen, indem man mehrere SQL-Befehle durch Semikolons getrennt in einen einzigen Befehl schreibt, was MySqlConnector akzeptiert. Die Parameter aller Befehle würden dann jedoch vermischt, und diese Syntax wird nicht von allen DBMS akzeptiert; die Batch-API ist die von ADO.NET festgelegte Standardform.

// eine [dao]-Schicht, die die Steuerstufen aus einer MySQL-Datenbank liest
public class MySqlTax : ITaxDao
{
    // für diese Implementierung spezifische Fehlercodes
    public enum ErrorCodes { Access = 101, Data = 102 }

    // die Standardabfrage: die Stufen müssen in aufsteigender Reihenfolge der Grenzen zurückgegeben werden
    public const string DefaultQuery = "select limits, coeffr, coeffn from brackets order by id";

    // Steuerstufen
    public TaxBracket[] TaxBrackets { get; }

    // Konstruktor: die Stufen werden ein für alle Mal gelesen
    public MySqlTax(string connectionString, string query = DefaultQuery)
    {
        List<TaxBracket> brackets = [];
        try
        {
            using var connection = new MySqlConnection(connectionString);
            connection.Open();
            using var command = new MySqlCommand(query, connection);
            using MySqlDataReader reader = command.ExecuteReader();
            // eine Stufe pro Zeile des Ergebnisses: limit, coeffR, coeffN
            while (reader.Read())
            {
                brackets.Add(new TaxBracket(reader.GetDecimal(0), reader.GetDecimal(1), reader.GetDecimal(2)));
            }
        }
        catch (MySqlException e)
        {
            // Fehler beim Datenbankzugriff: wir verpacken ihn in eine TaxException
            throw new TaxException("Error accessing the tax brackets database", e) { Code = (int)ErrorCodes.Access };
        }
        catch (Exception e) when (e is InvalidCastException or ArgumentOutOfRangeException)
        {
            // eine fehlende Spalte, vom falschen Typ oder mit dem Wert NULL
            throw new TaxException("The tax brackets of the database are incorrect", e) { Code = (int)ErrorCodes.Data };
        }
        // auch eine leere Tabelle ist ein Fehler
        if (brackets.Count == 0)
        {
            throw new TaxException("The database contains no tax bracket") { Code = (int)ErrorCodes.Data };
        }
        TaxBrackets = [.. brackets];
    }
}

    using System.Data.Common;
using Entities;

namespace Dao;

// eine [dao]-Schicht, die die Steuerstufen aus einer beliebigen Datenbank liest
// sie kennt nur die abstrakten Klassen von ADO.NET: der Connector wird ihr über seine Factory übergeben
public class DbTax : ITaxDao
{
    // Fehlercodes: dieselben wie bei MySqlTax
    public enum ErrorCodes { Access = 101, Data = 102 }

    // Steuerstufen
    public TaxBracket[] TaxBrackets { get; }

    // Konstruktor: die Factory des Connectors, die Verbindungszeichenfolge, die Abfrage, die die Stufen zurückgibt
    public DbTax(DbProviderFactory factory, string connectionString, string query)
    {
        List<TaxBracket> brackets = [];
        try
        {
            using DbConnection connection = factory.CreateConnection()
                ?? throw new InvalidOperationException("the connector cannot create a connection");
            connection.ConnectionString = connectionString;
            connection.Open();
            using DbCommand command = connection.CreateCommand();
            command.CommandText = query;
            using DbDataReader reader = command.ExecuteReader();
            while (reader.Read())
            {
                brackets.Add(new TaxBracket(reader.GetDecimal(0), reader.GetDecimal(1), reader.GetDecimal(2)));
            }
        }
        catch (DbException e)
        {
            throw new TaxException("Error accessing the tax brackets database", e) { Code = (int)ErrorCodes.Access };
        }
        catch (Exception e) when (e is InvalidCastException or ArgumentOutOfRangeException)
        {
            throw new TaxException("The tax brackets of the database are incorrect", e) { Code = (int)ErrorCodes.Data };
        }
        if (brackets.Count == 0)
        {
            throw new TaxException("The database contains no tax bracket") { Code = (int)ErrorCodes.Data };
        }
        TaxBrackets = [.. brackets];
    }
}

    10.11. Fazit

    Dieses Kapitel hat den Datenbankzugriff im verbundenen Modus mit ADO.NET behandelt:

    • Ein DBMS-spezifischer Konnektor (MySqlConnector für MySQL) stellt die Klassen [XxxConnection], [XxxCommand], [XxxDataReader] und [XxxTransaction] bereit, die von den abstrakten Klassen [DbConnection], [DbCommand], [DbDataReader] und [DbTransaction] aus [System.Data.Common] abgeleitet sind;
    • Eine Verbindung wird so spät wie möglich geöffnet und so früh wie möglich durch ein [using] geschlossen: Der Verbindungspool macht diese Praxis kostengünstig;
    • [ExecuteReader] führt ein [select] aus und liefert einen Reader, der mit [Read] zeilenweise durchlaufen wird; [ExecuteNonQuery] führt ein [insert], [update] oder [delete] aus und liefert die Anzahl der geänderten Zeilen; [ExecuteScalar] liefert einen einzelnen Wert;
    • Fehler sind [DbException] ([MySqlException] bei MySqlConnector);
    • Externe Werte werden immer über Parameter übergeben und niemals an den Abfragetext angehängt, was vor SQL-Injection schützt;
    • Transaktionen ([BeginTransaction], [Commit], [Rollback]) stellen sicher, dass eine Folge von Befehlen atomar ist (SQL);
    • Asynchrone Methoden ([OpenAsync], [ExecuteReaderAsync], [ReadAsync] …) und [await using] sind in Serveranwendungen Standard; Batches ([DbBatch]) verringern die Anzahl der Austauschvorgänge mit dem Server;
    • Der generische Konnektor ([DbProviderFactory], [DbProviderFactories]) macht den Code unabhängig vom DBMS, im Rahmen der Besonderheiten des jeweiligen DBMS.

    Version 6 der Anwendung [Tax] hat gezeigt, dass dank der Schichtenarchitektur der Wechsel von einer Datei zu einer Datenbank nur das Schreiben einer neuen [dao]-Schicht und die Änderung der Konfiguration erfordert. Im nächsten Kapitel erstellen wir eine siebte Version dieser Schicht mit Entity Framework Core, das die SQL-Befehle selbst erzeugt.
