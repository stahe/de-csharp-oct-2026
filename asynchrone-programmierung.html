    9. Asynchrone Programmierung

    Das vorherige Kapitel hat Threads eingeführt: Wir können mehrere Codeabschnitte „gleichzeitig“ ausführen, synchronisieren und dem Thread-Pool Aufgaben zuweisen. Dieses Kapitel, das im Kurs von 2008 nicht enthalten war, behandelt ein verwandtes, aber eigenständiges Problem: wie man ein Programm schreibt, das lange wartet (auf die Festplatte, das Netzwerk oder eine Datenbank), ohne bei diesen Wartezeiten Threads zu blockieren. Die Antwort in .NET liegt in zwei Schlüsselwörtern der Sprache C#, [async] und [await], und in einem Typ, [Task]. Sie sind heute allgegenwärtig: Die folgenden Kapitel werden sie verwenden, um auf Datenbanken zuzugreifen ([OpenAsync], [ExecuteReaderAsync], [ToListAsync], [SaveChangesAsync]), um TCP-Server ([AcceptTcpClientAsync]), Webclients ([HttpClient]) und Webdienste mit ASP.NET Core zu schreiben.

    Alle Beispiele dieses Kapitels sind Single-File-Anwendungen ([async-01.cs], [async-02.cs] …), die mit [dotnet run async-NN.cs] im Ordner [09-async] ausgeführt werden. Viele von ihnen messen Zeitdauern mit einer Stoppuhr ([Stopwatch]): Die angezeigten Millisekunden variieren von einer Ausführung zur anderen und von einem Rechner zum anderen (die Beispiele wurden auf einem Rechner mit zwei Prozessoren ausgeführt). Entscheidend sind die Größenordnungen: 1 Sekunde oder 3 Sekunden, 300 ms oder 0 ms.

    9.1. Warum Asynchronität

    9.1.1. Operationen, die warten

    Ein Programm erledigt zwei Arten von Arbeit:

    • Rechenaufgaben, die den Prozessor belegen: eine Liste sortieren, eine Steuer berechnen, einen Text analysieren;
    • Ein- und Ausgabe (E/A), die im Wesentlichen im Warten auf ein Peripheriegerät besteht: eine Datei von der Festplatte lesen, eine Anfrage an einen Webserver senden und auf dessen Antwort warten, eine SQL-Abfrage auf einem Datenbankserver ausführen.

    Die Größenordnungen sind sehr unterschiedlich. Ein Prozessor führt einige Milliarden Anweisungen pro Sekunde aus. Ein Lesevorgang auf einer Festplatte (SSD) dauert etwa eine zehntel Millisekunde; ein Hin- und Rückweg über ein lokales Netzwerk dauert den Bruchteil einer Millisekunde; ein Hin- und Rückweg zu einem Server am anderen Ende des Landes dauert einige zehn Millisekunden; und eine etwas komplexere SQL-Abfrage kann mitunter mehrere Sekunden dauern. Während dieser Wartezeiten hätte der Prozessor Millionen von Anweisungen ausführen können.

    Wenn ein Programm mit einer synchronen (blockierenden) Methode eine Zeile über eine Netzwerkverbindung liest, ist der Thread, der dieses Lesen ausführt, blockiert: Er tut nichts, existiert aber weiterhin. Er belegt Speicher (seinen Stack, in der Größenordnung von einem Megabyte), er ist dem Betriebssystem bekannt, und vor allem steht er nicht mehr zur Verfügung, um etwas anderes zu tun. In einem kleinen Konsolenprogramm, das jeweils nur eine Sache erledigt, ist das kein Problem. In zwei Situationen ist es dagegen ein viel größeres Problem:

    • auf einem Server: Jeder Client, der von einem blockierten Thread bedient wird, bindet diesen Thread. Der Kurs von 2008 erklärte dies bereits im Fazit seiner Behandlung des asynchronen TCP-Clients: Wenn der Thread-Pool N Threads hat und alle N Threads eine blockierende Operation ausführen, steht für einen neuen Client kein Thread mehr zur Verfügung. Ein moderner Webserver bearbeitet Tausende gleichzeitiger Anfragen mit nur wenigen Dutzend Threads: Das ist möglich, weil seine Threads bei der E/A nie blockiert werden;
    • in einer grafischen Benutzeroberfläche: Ein einzelner Thread – der UI-Thread – verarbeitet Klicks und zeichnet Fenster neu. Wird er durch einen Download blockiert, friert das Fenster ein.

    Asynchronität bedeutet, die E/A-Operation zu starten, den Thread freizugeben, während sie läuft (die Hardware und das Betriebssystem brauchen ihn nicht für die Datenübertragung), und die Arbeit nach Abschluss der Operation fortzusetzen, möglicherweise in einem anderen Thread:

    • In [1] startet der Thread T1 die E/A und bleibt blockiert, bis sie beendet ist;
    • in [2] startet der Thread T1 die E/A und kehrt in den Thread-Pool zurück, wo er andere Anfragen bearbeiten kann. Wenn die E/A-Operation abgeschlossen ist, benachrichtigt das System .NET, das einen Thread aus dem Pool – T2 (oder T1, falls er verfügbar ist) – den Rest der Verarbeitung ausführen lässt.

    // Warum Asynchronität: 100 Operationen, die jeweils eine Sekunde warten
// (ein Warten simuliert eine E/A-Operation: Lesen von der Festplatte, Netzwerkanfrage, SQL-Abfrage …)
using System.Diagnostics;

const int nbOperations = 100;
Console.WriteLine($"{nbOperations} operations of one second, {Environment.ProcessorCount} processors");

// 1 - ein Thread pro Operation, jeder Thread ist während des Wartens blockiert
var stopwatch = Stopwatch.StartNew();
var threads = new Thread[nbOperations];
for (int i = 0; i < nbOperations; i++)
{
    threads[i] = new Thread(() => Thread.Sleep(1000));
    threads[i].Start();
}
Display("1 - one thread per operation", ProcessThreads());
foreach (var thread in threads)
{
    thread.Join();
}
Display("    end");

// 2 - die Operationen werden an den Thread-Pool übergeben, blockieren ihn aber
stopwatch.Restart();
var tasks = new Task[nbOperations];
for (int i = 0; i < nbOperations; i++)
{
    tasks[i] = Task.Run(() => Thread.Sleep(1000));
}
Display("2 - thread pool, blocking waits", ProcessThreads());
Task.WaitAll(tasks);
Display("    end");

// 3 - asynchrone Wartezeiten: während des Wartens ist kein Thread blockiert
stopwatch.Restart();
for (int i = 0; i < nbOperations; i++)
{
    tasks[i] = Task.Delay(1000);
}
Display("3 - asynchronous waits", ProcessThreads());
await Task.WhenAll(tasks);
Display("    end");

// Anzahl der Threads des Prozesses, eine halbe Sekunde nach dem Start der Operationen
int ProcessThreads()
{
    if (stopwatch.ElapsedMilliseconds < 500)
    {
        Thread.Sleep(500 - (int)stopwatch.ElapsedMilliseconds);
    }
    using var process = Process.GetCurrentProcess();
    return process.Threads.Count;
}

// Anzeige der verstrichenen Zeit und, falls angegeben, der Anzahl der Threads
void Display(string message, int? nbThreads = null)
{
    string threadsInfo = nbThreads is null ? "" : $", {nbThreads,3} threads in the process";
    Console.WriteLine($"{message,-42} : {stopwatch.ElapsedMilliseconds,5} ms{threadsInfo}");
}

    • Zeilen 8–21: Die Lösung aus dem Kurs von 2008, ein Thread pro Operation. Jeder Thread führt [Thread.Sleep(1000)] aus: Er ist eine Sekunde lang blockiert. Die 100 Wartevorgänge laufen gleichzeitig ab, und der gesamte Vorgang dauert genau eine Sekunde (Zeile 4), jedoch um den Preis von 100 zusätzlichen Threads: Der Prozess hat nun mehr als 100 Threads (Zeile 3). Bei 10.000 Operationen wären 10.000 Threads erforderlich;
    • Zeilen 23–31: Die Operationen werden an den Thread-Pool delegiert ([Task.Run]), der im vorherigen Kapitel vorgestellt wurde. Der Pool startet mit so vielen Threads, wie es Prozessoren gibt (hier 2), und fügt nur schrittweise weitere hinzu, wenn alle ausgelastet sind, da er davon ausgeht, dass seine Threads Berechnungen durchführen und es nicht nötig ist, deutlich mehr Threads als Prozessoren zu haben. Hier rechnen die Threads aber nicht: Sie sind untätig. Die Operationen warten auf einen freien Thread, und der gesamte Vorgang dauert … mehr als zwanzig Sekunden (Zeile 6). Dies wird als „Thread-Pool-Starvation“ bezeichnet, der häufigste Fehler bei Servern, die Thread-Pools mit blockierender E/A kombinieren;
    • Zeilen 34–41: Die Wartevorgänge sind asynchron ([Task.Delay] statt [Thread.Sleep]). Während des Wartens ist kein Thread blockiert: Ein Systemtimer weckt .NET nach einer Sekunde. Der gesamte Vorgang dauert eine Sekunde, und die Anzahl der Threads steigt nicht (die in Zeile 7 angezeigten Threads sind diejenigen, die der Pool in Schritt 2 erzeugt hat; sie sind untätig);
    • Zeile 51: [Process.GetCurrentProcess()] ermöglicht den Zugriff auf den aktuell laufenden Prozess; seine Eigenschaft [Threads] ist die Sammlung seiner Threads (die von .NET und die des Systems).

    Merken wir uns die Lehre: Um zu warten, darf man keinen Thread blockieren. Asynchronität macht E/A nicht schneller; sie erlaubt es, viele E/A-Operationen gleichzeitig mit wenigen Threads zu bewältigen und die Threads, die die Anwendung braucht, verfügbar zu halten (den GUI-Thread, die Threads im Pool eines Servers).

    9.1.2. Drei aufeinanderfolgende Modelle

    .NET bot drei Möglichkeiten, asynchronen Code zu schreiben. Die ersten beiden findet man noch in Legacy-Code und älteren Artikeln, daher ist es nützlich, sie zu erkennen.

    Modell
    Ursprung
    Prinzip
    APM („Asynchronous Programming Model“)
    .NET 1.0 (2002)
    ein Methodenpaar: [BeginXxx] und [EndXxx]. [BeginXxx] startet die Operation und erhält eine Callback-Methode ([AsyncCallback]); die Callback-Methode, die am Ende der Operation von einem Thread aus dem Pool ausgeführt wird, ruft [EndXxx] auf, um das Ergebnis oder die Ausnahme abzurufen. Beispiel: [Socket.BeginConnect] / [EndConnect], verwendet vom asynchronen TCP-Client aus dem Kurs von 2008.
    EAP („Event-based Asynchronous Pattern“)
    .NET 2.0 (2005)
    eine Methode [XxxAsync], die die Operation startet, und ein Ereignis [XxxCompleted], das bei deren Abschluss ausgelöst wird. Beispiele: [WebClient.DownloadStringAsync] und [DownloadStringCompleted], die Klasse [BackgroundWorker] (Ereignisse [DoWork], [ProgressChanged], [RunWorkerCompleted]), die im Kurs von 2008 behandelt wurde.
    TAP („Task-based Asynchronous Pattern“)
    .NET 4.0 (2010), C# 5 (2012)
    eine Methode [XxxAsync] , die einen Task ([Task] oder [Task<T>]) zurückgibt, der die laufende Operation darstellt. Der aufrufende Code wartet mit dem Schlüsselwort [await] auf den Task. Dies ist das aktuelle Modell, das im weiteren Verlauf des Kurses ausschließlich verwendet wird.

    Die Muster APM und EAP haben denselben Nachteil: Der Code wird in Stücke zerlegt. Was natürlich als „verbinden, dann lesen, dann anzeigen“ gelesen wird, wird zu einer Methode, die die Verbindung startet, einer Callback-Methode, die das Lesen startet, und einer weiteren Callback-Methode, die die Daten anzeigt; Variablen müssen zwischen diesen Methoden geteilt werden, Ausnahmen werden an verschiedenen Stellen behandelt, und eine einfache Schleife („lesen, solange Daten vorhanden sind“) wird zu einer Callback-Methode, die sich rekursiv selbst aufruft, wie die Lesemethode ([lecture]) aus dem Kurs von 2008. Das TAP-Muster erlaubt es zusammen mit [async] und [await], asynchronen Code zu schreiben, der die Form von synchronem Code hat.

    Das Programm [async-02.cs] schreibt denselben TCP-Client nach den beiden extremen Modellen, APM und TAP. Es enthält außerdem einen kleinen Server, der von einem Thread ausgeführt wird und zwei Clients antwortet (die Netzwerkprogrammierung wird in Kapitel 12 ausführlich behandelt; vorerst genügt es zu wissen, dass ein Client sich mit dem Server verbindet und die Nachricht liest, die der Server ihm sendet).

    // derselbe TCP-Client, geschrieben mit dem APM-Modell von 2008 und anschließend mit dem aktuellen TAP-Modell
using System.Net;
using System.Net.Sockets;
using System.Text;

const int port = 27500;
// ein minimaler Server, ausgeführt von einem Thread: er bedient zwei Clients und endet dann
var listener = new TcpListener(IPAddress.Loopback, port);
listener.Start();
var server = new Thread(() =>
{
    for (int i = 1; i <= 2; i++)
    {
        using Socket service = listener.AcceptSocket();
        // der Server lässt sich mit der Antwort Zeit
        Thread.Sleep(500);
        service.Send(Encoding.UTF8.GetBytes($"Hello client no. {i}"));
    }
    listener.Stop();
});
server.Start();
Display("start of the program");

// 1 - das APM-Modell (Asynchronous Programming Model): BeginXxx / EndXxx und Callback-Methoden
var end = new ManualResetEventSlim(false);
byte[] buffer = new byte[1024];
var client = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
// wir starten den Verbindungsaufbau und geben die Methode an, die nach dessen Abschluss aufgerufen wird
client.BeginConnect(IPAddress.Loopback, port, Connected, client);
Display("APM: connection launched, the program goes on");
// der Hauptthread hat nichts mehr zu tun: er wartet auf das Signal der letzten Callback-Methode
end.Wait();

// Callback-Methode Nr. 1: die Verbindung ist hergestellt
void Connected(IAsyncResult result)
{
    // wir rufen das Objekt ab, das als letzter Parameter an BeginConnect übergeben wurde
    var socket = (Socket)result.AsyncState!;
    // wir beenden die Operation (erst EndConnect würde bei einem Fehlschlag die Ausnahme auslösen)
    socket.EndConnect(result);
    Display("APM: connected, read launched");
    // wir starten das Lesen der Serverantwort mit einer weiteren Callback-Methode
    socket.BeginReceive(buffer, 0, buffer.Length, SocketFlags.None, Received, socket);
}

// Callback-Methode Nr. 2: Daten sind eingetroffen
void Received(IAsyncResult result)
{
    var socket = (Socket)result.AsyncState!;
    int nbBytes = socket.EndReceive(result);
    Display($"APM: received [{Encoding.UTF8.GetString(buffer, 0, nbBytes)}]");
    socket.Close();
    // wir benachrichtigen den Hauptthread
    end.Set();
}

// 2 - das TAP-Modell (Task-based Asynchronous Pattern): XxxAsync und await
using (var client2 = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp))
{
    await client2.ConnectAsync(IPAddress.Loopback, port);
    Display("TAP: connected, read launched");
    int nbBytes = await client2.ReceiveAsync(buffer);
    Display($"TAP: received [{Encoding.UTF8.GetString(buffer, 0, nbBytes)}]");
}
server.Join();

// Ausgabe mit vorangestellter Nummer des Threads, der sie ausführt
static void Display(string message)
{
    Console.WriteLine($"[thread {Environment.CurrentManagedThreadId,2}] {message}");
}

    9.2. Tasks: Task und Task<T>

    Ein Task ist ein Objekt, das eine laufende oder abgeschlossene Operation darstellt:

    • [Task] stellt eine Operation dar, die kein Ergebnis zurückgibt;
    • [Task<T>] stellt eine Operation dar, die ein Ergebnis vom Typ [T] zurückgeben wird. [Task<T>] leitet sich von [Task] ab.

    Ein Task ist kein Thread. Ein Task kann von einem Thread aus dem Pool ausgeführt werden (wie bei Tasks, die mit [Task.Run] erzeugt werden), aber viele Tasks werden von keinem Thread ausgeführt: Der von [Task.Delay(1000)] zurückgegebene Task wird nach einer Sekunde einfach von einem Timer „abgeschlossen“; der von [ReceiveAsync] zurückgegebene Task wird abgeschlossen, wenn das System signalisiert, dass Daten eingetroffen sind. Ein Task ist ein Versprechen auf ein Ergebnis, das abgefragt (Ist er beendet? War er erfolgreich?) und auf das gewartet werden kann.

    // Tasks: Erstellung, Warten, Status, Ergebnis, Fortsetzung

// 1 - Task.Run übergibt eine Verarbeitung an den Thread-Pool und gibt einen Task<T> zurück
Task<long> task1 = Task.Run(() =>
{
    // eine Berechnung von einigen Zehntelsekunden
    long sum = 0;
    for (int i = 1; i <= 200_000_000; i++)
    {
        sum += i % 7;
    }
    return sum;
});
Console.WriteLine($"task1 launched, status: {task1.Status}");
// await unterbricht das Programm bis zum Ende des Tasks und liefert dessen Ergebnis
long result = await task1;
Console.WriteLine($"task1 finished, status: {task1.Status}, result: {result}");

// 2 - Task.Delay gibt einen Task zurück, der nach einer Verzögerung endet, ohne einen Thread zu belegen
Task task2 = Task.Delay(300);
Console.WriteLine($"task2 launched, status: {task2.Status}");
await task2;
Console.WriteLine($"task2 finished, status: {task2.Status}");

// 3 - Tasks, die bereits abgeschlossen sind
Task<int> task3 = Task.FromResult(42);
Task task4 = Task.CompletedTask;
Console.WriteLine($"task3: status {task3.Status}, result {await task3} ; task4: status {task4.Status}");

// 4 - ein fehlschlagender Task: await löst seine Ausnahme erneut aus
Task<int> task5 = Task.Run(() => int.Parse("abc"));

    • Zeilen 4–12: [Task.Run] weist dem Thread-Pool eine Funktion zu und gibt sofort einen Task zurück, der ihre Ausführung darstellt. Die Funktion gibt einen [long] zurück, daher hat der Task den Typ [Task<long>]. [Task.Run] ist das Werkzeug für Berechnungen, die im Hintergrund ausgeführt werden sollen; es darf nicht dazu verwendet werden, eine blockierende E/A-Operation „asynchron zu machen“ (wie es Schritt 2 von [async-01.cs] getan hat);
    • Zeile 14: Die Eigenschaft [Status] gibt den Zustand des Tasks zurück. Unmittelbar nach dem Start wartet der Task hier darauf, dass ein Thread aus dem Pool ihn übernimmt ([WaitingToRun]); je nach Auslastung des Rechners kann auch [Running] (läuft) erscheinen;
    • Zeile 16: [await task1] wartet auf das Ende des Tasks, ohne den Thread zu blockieren, und gibt sein Ergebnis zurück, das hier den Typ [long] hat. Der Ausdruck [await t] hat den Typ [T] , wenn [t] den Typ [Task<T>] hat, und hat keinen Wert, wenn [t] den Typ [Task] hat;
    • Zeile 20: [Task.Delay(300)] gibt einen Task zurück, der in 300 ms abgeschlossen sein wird. Während dieser Zeit ist kein Thread belegt. Dies ist das asynchrone Äquivalent zu [Thread.Sleep(300)]. Sein Zustand, [WaitingForActivation], bedeutet „wartet auf ein externes Ereignis“;
    • Zeilen 26–27: [Task.FromResult(42)] gibt einen Task zurück, der bereits mit dem Ergebnis 42 abgeschlossen ist, während [Task.CompletedTask] einen Task zurückgibt, der bereits ohne Ergebnis abgeschlossen ist. Sie werden verwendet, wenn eine Methode einen Task zurückgeben muss, das Ergebnis aber bereits vorliegt (zum Beispiel ein zwischengespeicherter Wert);
    • Zeilen 31–36: Ein Task, dessen Funktion eine Ausnahme auslöst, endet mit dem Zustand [Faulted]. Die Ausnahme wird im Task aufbewahrt, und [await] löst sie erneut aus; sie wird mit einem gewöhnlichen [try / catch] abgefangen;
    • Zeilen 42–48: [Wait()] wartet auf das Ende des Tasks, indem es den aktuellen Thread blockiert, und die Eigenschaft [Result] gibt das Ergebnis eines [Task<T>] zurück und blockiert dabei ebenfalls den Thread, wenn der Task nicht beendet ist. Dies sind die Formen des Thread-Wartens aus dem vorherigen Kapitel ([Join]). Sie sollten vermieden werden: Sie haben alle Nachteile blockierender E/A, verpacken Ausnahmen in eine [AggregateException] (Zeile 56) und können in einer grafischen Anwendung einen Deadlock verursachen. Sie sollten den seltenen Fällen vorbehalten bleiben, in denen Sie wissen, dass der Task bereits abgeschlossen ist;
    • Zeile 51: [ContinueWith] hängt an einen Task eine Fortsetzung an – eine Funktion, die ausgeführt wird, wenn der Task abgeschlossen ist. Die Fortsetzung erhält den abgeschlossenen Task und gibt hier eine ganze Zahl zurück: Daraus entsteht ein neuer Task, [Task<int>]. So wurde mit .NET 4.0 asynchroner Code geschrieben, vor [await]; [await] beruht auf einem ähnlichen Mechanismus (Registrierung einer Abfolge, die am Ende des Tasks ausgeführt wird), den der Compiler jedoch sicherer umsetzt. [ContinueWith] wird kaum noch direkt verwendet;
    • Zeilen 54–56: die Booleschen Eigenschaften [IsCompleted] (beendet, gleichgültig wie), [IsCompletedSuccessfully] (erfolgreich beendet), [IsFaulted] (mit einer Ausnahme beendet), [IsCanceled] (abgebrochen) und die Eigenschaft [Exception] vom Typ [AggregateException], die die Ausnahme(n) des Tasks enthält.

    9.3. Asynchrone Methoden: async und await

    9.3.1. Eine asynchrone Methode schreiben

Es sind die erwarteten Operationen ([Task.Delay], asynchrone E/A), die tatsächlich asynchron sind.

Task<int> CountSugarsAsync(int count)
{
    var machine = new CountSugarsMachine { count = count, state = 0 };

    return machine.ResultTask; // der Task, den die Zustandsmaschine später abschließen wird

class CountSugarsMachine
{
    public int count, i, state;               // die lokalen Variablen werden zu Feldern
    public TaskCompletionSource<int> Source = new();
    public Task<int> ResultTask => Source.Task;

    public void Advance()
    {
        if (state == 0) { i = 1; }             // erster Durchlauf: Beginn der Schleife
        else { Console.WriteLine($"  sugar no. {i}"); i++; }   // Fortsetzung nach dem await
        if (i <= count)
        {
            state = 1;
            // wir bitten darum, am Ende der Verzögerung aufgerufen zu werden, und geben dann die Kontrolle zurück
            Task.Delay(200).GetAwaiter().OnCompleted(Advance);
            return;
        }
        Source.SetResult(count);               // Ende der Methode: der Task ist abgeschlossen
    }
}

    Dies folgt demselben Prinzip wie die Callback-Methoden im APM-Modell ([OnCompleted(Advance)] fordert am Ende der Operation einen Callback an), aber der Compiler zerlegt die Methode, sichert die Variablen und behandelt die Ausnahmen. Der Entwickler schreibt dagegen eine Methode, die sich von oben nach unten liest. Den tatsächlich erzeugten Code können Sie mit einem Decompiler wie ILSpy oder auf der Website SharpLab ansehen; er ist deutlich länger, insbesondere weil er den Fall behandelt, dass der erwartete Task bereits abgeschlossen ist (dann läuft die Ausführung ohne Unterbrechung weiter), sowie den Fall von Ausnahmen.

Asynchronität erleichtert die E/A-Nebenläufigkeit; sie macht Berechnungen nicht schneller.

    9.6. Abbruch und Timeouts

    9.6.1. CancellationTokenSource und CancellationToken

    Eine lang laufende asynchrone Operation muss abbrechbar sein: Der Benutzer hat auf [Cancel] geklickt, ein Client eines Webservers hat die Verbindung getrennt, die Anwendung wurde beendet oder ein Timeout wurde überschritten. .NET verwendet hierfür einen kooperativen Mechanismus mit zwei Objekten:

    • eine [CancellationTokenSource] (Abbruchquelle), die vom Code gehalten wird, der den Abbruch beschließt. Ihre Methode [Cancel()] fordert den Abbruch an; [CancelAfter(delay)] fordert ihn nach einer Zeitspanne automatisch an;
    • ein [CancellationToken] (Abbruchtoken), das über die Eigenschaft [Token] der Quelle bezogen und als Parameter an abbrechbare Operationen übergeben wird. Die Operation prüft das Token ([IsCancellationRequested]) oder lässt es eine Ausnahme auslösen, falls ein Abbruch angefordert wurde ([ThrowIfCancellationRequested()]), und reicht es an die von ihr aufgerufenen Operationen weiter.

    Der Mechanismus ist kooperativ: Niemand unterbricht eine Operation gewaltsam (die Methode [Thread.Abort] aus dem Kurs von 2008 ist im aktuellen .NET veraltet: Sie löst lediglich eine [PlatformNotSupportedException] aus); die Operation hält von selbst an, und zwar an einer Stelle, an der sie dies sauber tun kann. Per Konvention endet eine abgebrochene Operation mit dem Auslösen einer [OperationCanceledException], und ihr Task hat den Status [Canceled].

        sum += i % 7;
    }
    return sum;
}

    • Zeilen 6–17: Die Quelle wird in einem [using] erzeugt, weil sie einen Timer verwendet, der freigegeben werden muss. [CancelAfter] fordert den Abbruch nach 1,2 Sekunden an: Der Download erhält drei Blöcke und hält dann bei 1.200 ms an (Zeile 5). Wir fangen [OperationCanceledException] ab, die Basisklasse, die alle Abbrüche erfasst;
    • Zeilen 21–33: eine synchrone Berechnung (kein Warten), die abgebrochen werden kann. Die Methode [Compute] (Zeilen 67–79) prüft das Token alle eine Million Iterationen mit [ThrowIfCancellationRequested()], das eine [OperationCanceledException] auslöst, wenn ein Abbruch angefordert wurde. // eine auf [timeout] Millisekunden begrenzte Verarbeitung, die auch vom Aufrufer gestoppt werden kann
async Task ProcessWithTimeoutAsync(string name, int duration, int timeout, CancellationToken stop)
{
    // die verknüpfte Quelle wird abgebrochen, sobald eine der beiden Ursachen eintritt

    linked.CancelAfter(timeout);
    try
    {

    }
    catch (OperationCanceledException) when (stop.IsCancellationRequested)
    {
        Display($"3 - {name} : stopped at the caller's request");
    }
    catch (OperationCanceledException)
    {
        Display($"3 - {name} : timeout of {timeout} ms exceeded");
    }
}

    9.9. Asynchrone Streams: IAsyncEnumerable<T>

    Eine asynchrone Methode liefert nach einer gewissen Zeit ein Ergebnis. Ein Iterator (eine Methode, die einen [IEnumerable<T>] mit [yield return] zurückgibt) liefert eine Folge von Ergebnissen, die bei Bedarf erzeugt werden.     • er wird von einer [async]-Methode erzeugt, die [IAsyncEnumerable<T>] zurückgibt und sowohl [await] als auch [yield return] enthält;
    • er wird mit [await foreach] konsumiert.

    public int NbServerAccesses { get; private set; }
    public int NbCacheAccesses { get; private set; }

    // ValueTask<decimal>: keine Task-Allokation, wenn das Ergebnis im Cache liegt
    public ValueTask<decimal> ReadRateAsync(string code)
    {
        if (cache.TryGetValue(code, out decimal rate))
        {
            // schneller und synchroner Pfad: das Ergebnis ist bereits bekannt
            NbCacheAccesses++;
            return ValueTask.FromResult(rate);

            "USD" => 1.17m,
            "GBP" => 0.87m,
            _ => throw new ArgumentException($"unknown currency: {code}"),
        };
        cache[code] = rate;
        return rate;
    }

    9.10.2. ConfigureAwait und der Synchronisierungskontext

    Das Programm [async-05.cs] hat gezeigt, dass in der Konsole der Rest einer Methode nach einem [await] von irgendeinem Thread des Pools ausgeführt wird. In einer grafischen Anwendung (Windows Forms, WPF, MAUI) ist das nicht der Fall. Eine grafische Komponente darf nur vom UI-Thread bearbeitet werden: Der Kurs von 2008 musste in seinen Callback-Methoden [listBoxEvts.Invoke(...)] verwenden, damit die Aktualisierung von diesem Thread ausgeführt wurde. Mit [await] ist das nicht mehr nötig: Der Oberflächen-Thread besitzt einen Synchronisierungskontext ([SynchronizationContext.Current] ist nicht [null]), den [await] speichert; nach dem Warten wird der Rest der Methode an diesen Kontext zurückgegeben und somit vom Oberflächen-Thread ausgeführt.     • Im Code einer universell einsetzbaren Bibliothek (die keine grafische Benutzeroberfläche behandelt und nicht weiß, wer sie aufruft) verwenden Sie [ConfigureAwait(false)] bei jedem [await]: Das ist etwas effizienter und verhindert Deadlocks, falls ein unvorsichtiger Aufrufer [.Result] verwendet;
    • im Code von Anwendungen (grafische Benutzeroberfläche, Konsolenprogramm, ASP.NET-Core-Anwendung) wird es nicht geschrieben. Konsolenprogramme und ASP.NET-Core-Anwendungen haben ohnehin keinen Synchronisierungskontext: [ConfigureAwait(false)] macht dort keinen Unterschied.

    Die Beispiele dieses Kurses, bei denen es sich um Anwendungen handelt, verwenden [ConfigureAwait] nicht.

    9.10.3. TaskCompletionSource<T>: ein Ereignis in einen Task umwandeln

// wandelt die MeasureTaken-Ereignisse des Thermometers in einen Task um
static Task<double> WaitForTemperatureAsync(Thermometer thermometer, double threshold, CancellationToken token)
{
    // die Quelle eines Tasks, den wir selbst abschließen
    var source = new TaskCompletionSource<double>(TaskCreationOptions.RunContinuationsAsynchronously);
    // die Registrierung beim Abbruch-Token, die freizugeben ist, wenn der Task abgeschlossen ist
    CancellationTokenRegistration registration = default;
    // der Ereignishandler schließt den Task ab, wenn der Schwellenwert erreicht ist
    void OnMeasure(object? sender, double temperature)
    {
        if (temperature >= threshold && source.TrySetResult(temperature))
        {
            thermometer.MeasureTaken -= OnMeasure;
            registration.Dispose();
        }
    }
    thermometer.MeasureTaken += OnMeasure;
    // eine Abbruchanforderung schließt den Task mit dem Status Canceled ab
    registration = token.Register(() =>
    {
        if (source.TrySetCanceled(token))
        {
            thermometer.MeasureTaken -= OnMeasure;
        }
    });
    // der Task wird sofort zurückgegeben; er wird später abgeschlossen
    return source.Task;
}

    9.11. Asynchrone Parallelität

    9.11.1. Parallel.ForEachAsync

    [Task.WhenAll] startet alle Operationen gleichzeitig.     9.11.2. Producer/Consumer: System.Threading.Channels

    Das vorige Kapitel führte das Muster Producer/Consumer anhand der Sammlung [BlockingCollection<T>] ein: Producer-Threads stellen Elemente in eine Warteschlange, Consumer-Threads entnehmen sie; [Take] (oder die Aufzählung [GetConsumingEnumerable]) blockiert einen Consumer, solange die Warteschlange leer ist, während [Add] einen Producer blockiert, solange eine begrenzte Warteschlange voll ist. Diese Wartevorgänge blockieren Threads. Channels im Namespace [System.Threading.Channels] (.NET Core 3.0) bieten denselben Dienst mit asynchronem Warten:

    • [Channel.CreateBounded<T>(capacity)] erzeugt einen begrenzten Channel, [Channel.CreateUnbounded<T>()] erzeugt einen unbegrenzten Channel;
    • die Eigenschaft [Writer] ([ChannelWriter<T>]) wird von Producern verwendet: [WriteAsync] veröffentlicht ein Element (und wartet asynchron, bis Platz frei wird), [TryWrite] versucht, es sofort hinzuzufügen, [Complete] zeigt an, dass keine weiteren Elemente mehr folgen;
    • Die Eigenschaft [Reader] ([ChannelReader<T>]) wird von Consumern verwendet: [ReadAsync] ruft ein Element ab, während [ReadAllAsync] einen asynchronen Stream aller Elemente zurückgibt, der endet, wenn der Channel durch [Complete] geschlossen und leer ist.

// der Produzent: eine Bestellung alle 50 ms
async Task ProduceAsync(ChannelWriter<int> writer, int nbOrders)
{
    for (int i = 1; i <= nbOrders; i++)
    {
        await Task.Delay(50);
        // TryWrite verwirft die Bestellung sofort, wenn im Channel Platz ist
        if (writer.TryWrite(i))
        {
            Display($"P  : order {i} dropped");
        }
        else
        {
            // Channel voll: WriteAsync wartet (ohne einen Thread zu blockieren), bis ein Platz frei wird
            Display($"P  : channel full, order {i} waits");
            await writer.WriteAsync(i);
            Display($"P  : order {i} dropped");
        }
    }
    // es wird nichts mehr geschrieben: die Konsumenten verlassen ihre Schleife
    writer.Complete();
    Display("P  : end of the production");
}

// ein Konsument: die Verarbeitung einer Bestellung dauert 400 ms
async Task ConsumeAsync(string name, ChannelReader<int> reader)
{
    // ReadAllAsync gibt einen asynchronen Datenstrom zurück, der endet, wenn der Channel geschlossen und leer ist
    await foreach (int order in reader.ReadAllAsync())
    {
        Display($"{name} : processing of order {order}");
        await Task.Delay(400);
    }
    Display($"{name} : no more orders");
}

static async Task<int> CalculateTaxesAsync(TaxBracket[] brackets, string input, string output, CancellationToken token)
{
    int nbLines = 0;
    await using var writer = new StreamWriter(output);
    await foreach (string line in File.ReadLinesAsync(input, token))
    {
        string[] fields = line.Split(' ', StringSplitOptions.RemoveEmptyEntries);
        string result = fields switch
        {

            _ => "incorrect line",

    return nbLines;
}

static int CalculateTax(TaxBracket[] brackets, bool married, int nbChildren, int salary)
{
    decimal shares = married ? nbChildren / 2m + 2 : nbChildren / 2m + 1;
    if (nbChildren >= 3)
    {
        shares += 0.5m;

    decimal income = 0.72m * salary;

}

    9.14. Die goldenen Regeln

    Fassen wir die Regeln der asynchronen Programmierung mit .NET zusammen:

    • async durchgängig: Eine Methode, die auf eine asynchrone Operation wartet, wird selbst asynchron ([async Task]), und ebenso ihre Aufrufer, bis hin zum Einstiegspunkt ([Main] asynchron, Ereignishandler, Controller-Aktion in ASP.NET Core). Das Vermischen von asynchronem Code mit blockierendem Warten hebt die Vorteile der Asynchronität auf;
    • verwenden Sie nicht [.Result], [.Wait()] oder [Task.WaitAll] bei einem unbeendeten Task: Nutzen Sie stattdessen [await], [Task.WhenAll], [Task.WhenAny] oder [Task.WhenEach]. Diese blockierenden Formen frieren einen Thread ein und können in grafischen Anwendungen dauerhafte Deadlocks verursachen;
    • verwenden Sie [Thread.Sleep] nicht in asynchronem Code: Nutzen Sie stattdessen [await Task.Delay(...)];
    • schreiben Sie keine [async void]-Methoden, außer in GUI-Ereignishandlern; eine asynchrone Methode sollte [Task] oder [Task<T>] zurückgeben (in Ausnahmefällen [ValueTask<T>]);
    • der Name einer asynchronen Methode endet auf [Async]: [CalculateTaxesAsync], [ReadRateAsync];
    • eine abbrechbare asynchrone Methode erhält ein [CancellationToken] als letzten Parameter und reicht es an alle asynchronen Operationen weiter, die sie aufruft; eine abgebrochene Operation endet mit einer [OperationCanceledException];
    • [Task.Run] ist Berechnungen vorbehalten, die Sie im Hintergrund ausführen möchten (etwa um zu vermeiden, dass ein GUI-Thread blockiert wird). Verpacken Sie keine synchrone Ein-/Ausgabeoperation in [Task.Run] , um sie „asynchron zu machen“: Verwenden Sie die Version [XxxAsync] der Operation;
    • erst starten, dann warten: Um mehrere unabhängige Operationen gleichzeitig auszuführen, starten Sie alle und warten dann mit [Task.WhenAll] auf sie; um die Anzahl der Operationen zu begrenzen, verwenden Sie [Parallel.ForEachAsync] oder einen Channel;
    • [ConfigureAwait(false)] wird in Bibliotheken verwendet, nicht in Anwendungen;
    • auf einen gestarteten Task muss gewartet werden (oder er wird ausdrücklich mit [_ =] ignoriert, wobei seine Ausnahmen zu behandeln sind): Ein vergessener Task verbirgt seine Ausnahmen und kann durch das Programmende unterbrochen werden.
